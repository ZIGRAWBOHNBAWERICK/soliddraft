# Continuous integration

`hosted.yml` runs on pushes, pull requests and manual dispatch. STEP validation and application scenarios use `boat`, with four cores and 8 GB RAM, when the repository variable `USE_BOAT` is `true`. Both jobs were faster on boat in two measurements. A full PR run uses two boat starts; the plan allows 200 daily starts. Each job's `runs-on` expression holds its size choice in one place. Other build and test jobs, macOS, Windows, packaging and release stay on GitHub. Selection and the gate retain `USE_LOCAL_RUNNERS`, which is off on this repository. All jobs use read-only repository permissions.

Boat runs require `github.repository` to be `ZIGRAWBOHNBAWERICK/soliddraft`, and both `github.actor` and `github.triggering_actor` to be `BohnBawerick`. Pull requests must also come from that repository and have `BohnBawerick` as their author. Forks, Dependabot, other authors and other users' reruns use `ubuntu-latest`. [Boat's public-repository rules](https://docs.boat.dev/ci.md#public-repositories) require both the run author and the user starting it to be allowed, even on reruns. The extra PR author check prevents an owner's rerun from moving another author's PR onto boat.

Set `USE_BOAT=false` with `gh-axi variable set USE_BOAT --body false` to return every moved job to `ubuntu-latest` without a workflow change. Set it back to `true` to resume boat. No boat key or CI secret is needed. Rust cache and artifact actions remain the GitHub Actions steps. The `USE_BOAT` switch is the fallback; there is no automatic failover.

The Linux workspace build and four shards stay on GitHub. Three shards spent 42-46 minutes downloading the 2.1 GB nextest archive on both four-core and eight-core boat machines. One shard on each size downloaded it in under four minutes, so adding cores did not remove the transfer delay. No quick workflow fix was established. Lint, kernel, MSRV, web and interactive Linux also stay on GitHub because their measured boat times did not show a consistent improvement. The PR records the timings and the cancelled eight-core run.

Pull requests run the affected crates and their consumers on Linux. The selector uses Cargo metadata, including optional, test and target dependencies, and keeps base-manifest dependencies for renamed or deleted code. Platform source, manifests, lockfiles, toolchains, packaging and GPU-backend edits also select macOS tests and the macOS rendered bracket under the rules below. Release-branch pushes and normal manual dispatch run every hosted and packaging unit except Windows, which is [deferred](#windows-is-deferred). Main pushes with non-CI changes run all Linux units as a selection audit. At 23:17 UTC each night, Hosted CI runs every Linux, macOS and packaging unit on main, with full workspace archives, documentation tests and all application scenarios. Windows remains deferred. Scheduled runs use the normal gate and retain independent evidence like main pushes; they do not depend on a changed-file diff. In a mixed change, a file under `ci/` also selects the jobs that read it, listed under [CI file consumers](#ci-file-consumers). Workflow edits in a mixed change and unknown paths broaden to all units. Both the base and candidate selection rules apply. All builds use a checkout with no submodules. Linux also runs formatting, clippy, the browser application build and Rust 1.88 checks for the crates that still support it. The browser build compiles Catallax into the same `wasm32-unknown-unknown` module as the application. Linux and macOS also drive the rendered Catallax bracket and drawing flows, retaining screenshots and part files as artifacts. No job needs SMLib, Emscripten or a C++ kernel toolchain.

A Catallax revision-only change in `Cargo.lock` or a `Cargo.toml` selects all eight Linux units, including the adapter and recipe tests, app scenarios, rendered bracket and STEP validation. In `Cargo.lock` the Catallax source revision must move, and every added, removed or changed package table must come from the official Catallax repository. This allows Catallax crates that the bump adds or removes, and new edges from Catallax crates to packages already locked. Package source decides, not package name. Every other package table must stay the same, including workspace members, so a new third-party crate keeps the broad rules. A manifest may change only the `rev` of dependencies from the official Catallax repository; adding a dependency to an application manifest, even a Catallax one, keeps the broad rules. Other edits in the same diff still add their required checks. macOS checks revision-only kernel moves at release, accepting that a kernel difference visible only on one platform may reach main first.

Changes limited to `.github/workflows/`, `ci/` and `docs/ci.md` run lint, its Python CI tooling tests and the jobs whose own workflow definitions changed. Editing several jobs selects those jobs only. Changes to a shared workflow `env` or `defaults` select that workflow's jobs; unreadable workflow structure or shared YAML nodes retain the broad rules. Package workflow edits select the affected package definitions. Selector, gate, registry, helper and documentation edits alone need only lint. Scenario JSON edits additionally run the application job and Linux workspace tests because Rust regressions also read those fixtures. The select job and gate still run. Source and lockfile changes keep the normal selection rules, including CI consumers, and explicit qualification dispatches and release branches retain their full checks. Both the accepted base selector and candidate selector apply, so a policy edit cannot remove checks still required by the base.

So are the native window, GPU setup and dialog files `soliddraft-app/src/main.rs`, `app/workspace.rs` and `platform.rs`, and `soliddraft-cli/src/screenshot.rs`, whatever they contain. `edit-speed.yml` times the five ordinary edits on a pull request that touches the kernel interface, the Catallax adapter or the model. `ci/edit_speed.py` builds the fork point and the head, alternates them on one CPU with one warmup pair and nine measured pairs, and writes click and topology medians to the run summary and the `edit-speed` artifact. A difference in a part file, recipe, kernel question, view or command answer fails the job. Timing never does, and kernel work may differ between the two revisions. The job sits outside the merge gate. A pull request that moves the Catallax pin runs two kernels, whose answers may rightly differ, so each revision is compared only with its own runs and the summary labels the medians as a pin move, not a same-kernel comparison.

The same job writes the CPU model from `lscpu` and a calibration figure above the medians, and keeps both in `host.json`, `lscpu.txt` and `report.json` in the artifact. The figure is the fastest of seven rounds of a fixed pure-Python workload on the pinned CPU, so it uses no SolidDraft or Catallax code. A different Python version moves it, so it is printed with the Python version. Read the results by these rules:

- Take a percent reduction only from pairs in one job.
- A one second verdict names the CPU it was measured on.
- Do not compare runs on different CPUs in milliseconds.

## Windows is deferred

By the captain's decision, CI builds and checks the browser, Linux and macOS only until a later Windows catch-up. No pull request, main push, release branch, tag or full qualification selects `test-windows` or `package-windows`, and releases publish no Windows packages. Windows product code stays in the tree, unbuilt by CI, so a Windows-only fault can land unnoticed until the catch-up.

The routing rules still name Windows, and the frozen routing fixtures still pin them. `select()` in `ci/select-checks.py` drops the two units last, and the accepted selector goes through the same function. The `test-windows` job, the Windows package cell and both registry entries stay defined. The merge gate skips Windows when it is unselected. When Windows is selected, the gate requires it to be green like any other unit.

To catch up, dispatch Hosted CI manually with `windows_catch_up` on. That is the only way to select Windows: the selector ignores the input on any other event, and `release.yml` passes no input to `packages.yml`, so its dry runs and tags have no Windows path. The run is a full qualification plus both Windows units, and takes 2 to 3 hours on Windows. Branch `fm/sdc-ci-round4-windows-shards-parked` holds unfinished work to split those tests across runners.

## CI file consumers

`ci/check-consumers.json` names every file under `ci/` and the jobs that read it. `files` maps exact paths to unit names, or to `"all"` for every unit and package. `patterns` maps full-match regular expressions to unit names. Lint always runs, so an empty list means no other job reads the file.

The selector looks up every changed `ci/` path, for all statuses and for both sides of a rename or copy. A deleted or renamed-away path may use the base map. The result is united with every other path's selection, main pushes with non-CI changes retain all eight Linux units, and release branches and normal manual dispatch retain every unit and package except the deferred Windows ones. The explicit baseline refresh dispatch is separate and selects only its generators.

Every tracked file under `ci/` needs exactly one entry, even when the diff does not touch it or another path already selects everything. An unmapped file, an invalid map or a path with two matching entries makes `ci/select-checks.py` exit nonzero without writing a selection, on every event, so the `select` job and the merge gate fail. A new script needs an exact entry, and adding that entry keeps CI-only changes on lint; a mixed change also applies the normal consumer rules. A new one-level scenario file matches the pattern and needs no map edit.

The running selector and its map are the candidate policy; `--head` names the tree they judge. The accepted selector runs from the base commit with the base map, so a candidate map edit cannot remove a consumer. If the accepted selector cannot judge a path, or its map is unreadable, every unit and package except the deferred Windows ones is selected and the `base:` reason says why. A commit whose selector predates the map has no base map to read, and its older rules apply.

## Superseded runs

Hosted CI has a concurrency group keyed on the pull request's head branch (the pushed ref for a manual run), so a new push cancels that branch's older runs. A run on main is never cancelled: its group is its own run id, so no later push shares it and GitHub's replacement of a waiting run in a shared group cannot drop a main result. `ci/test_workflows.py`, run in the lint job, evaluates the group and cancel expressions for pull request, manual and main runs, and for a pull request from a branch that is itself called `main`.

## Reliability tests

Four property-test files use `proptest` as a dev-dependency. Each runs a fixed number of cases from a fixed seed by default, so a failure reproduces, and prints the failing input and does not write regression files. To search further, set `PROPTEST_CASES` and `PROPTEST_RNG_SEED`, for example `PROPTEST_CASES=2000 PROPTEST_RNG_SEED=7 cargo test -p soliddraft-app --test command_fuzz`. A failure found that way becomes a named test beside the fix.

| File | Input fuzzed | Properties |
|---|---|---|
| `crates/soliddraft-assistant/tests/protocol_fuzz.rs` | The MCP server's JSON-RPC layer, the schema check, the stdio line loop and the HTTP endpoint: arbitrary JSON, text, ids, batches, nesting, non-UTF-8 lines, oversized lines, malformed requests, lying `Content-Length` | No panic; every request gets a well-formed reply that names an error when the input was bad; the server answers the next message; no error echoes the input back whole |

`crates/soliddraft-cli/tests/kernel_abort.rs` holds the isolated reproductions of a known Catallax abort (a plane origin a hair off zero overflows the stack of the main thread, in about 20 s). They are ignored until the pinned Catallax revision bounds that recursion (the Catallax fix is in progress); run them with `-- --ignored`. A green `recipe_fuzz` or `command_fuzz` run does not cover those inputs, nor lengths over 100 m (refused before the kernel), nor a mutated bracket; each exclusion is stated in the generator's doc comment and comes out with the `#[ignore]` lines. `recipe_fuzz` and `command_fuzz` keep nonzero numbers smaller than 0.01 out of their inputs for the same reason.

`crates/soliddraft-cli/tests/damaged_files.rs` opens truncated, corrupted and wrong-version variants of a part, an assembly and a drawing through the libraries, the application's open functions and the binary's reading and writing commands. Each must be refused with a typed error of the right kind (damage, or a version or kind this build does not read) and a message, and the file's bytes, hash and folder must be unchanged afterwards. `soliddraft doc info`, `doc refs`, `doc where-used`, `doc migrate` and `asm insert` of a part read the manifest alone, so they report a file whose manifest reads even when the truth entry is damaged; opening it is what refuses.

`FUZZ_TRACE=1 cargo test ... -- --nocapture` prints each command-line run's exit status and arguments, and each tool call's outcome in `command_fuzz`.

The `countersink` acceptance scenario extends its original seven steps with a boss beside the countersinks, a third hole and diameter edit, face-name checks, save/reopen and fresh-process checked STEP export. Its last step requires the typed refusal for a countersink that truly meets the boss wall and verifies unchanged geometry. Volume and bounds expectations come from the V8 merge B test design.

## Configuration acceptance

`ci/scenarios/configurations.json` checks three width variants against hand-derived volume, area, centroid and bounds, then checks exact geometry identity across undo, redo, switches and reopens. Two checked STEP exports must match the selected variant. The scenario records click timings. S13 checks zero-depth refusal by setting the depth-only `flange_d` global to zero, and a valid row whose cut would empty the body. Zero width is now rejected earlier by sketch-length validation, so it cannot serve as the depth-only witness. Activation must preserve the previous variant; switching and repairing that row then prove recovery. Model cases M1-M9 cover old files, display meshes, inheritance, write targets, rename, row validation, undo and damaged truth. Command fuzzing includes configuration edits and switches.

`ci/scenarios/configuration-grid-csv.json` and `-xlsx.json` run one journey per format against an independent fixture and hand-derived geometry: preview, Cancel, Apply, undo, redo, both exports, a fresh process, checked STEP and every row. `ci/scenarios/configuration-title.json` binds a drawing title and proves it follows the accepted source through part switches, undo, a fresh process and a part changed on disk. `ci/configuration-grid-fixtures.py` is the test designer's generator, and `ci/check-configuration-grid.py` decodes exported CSV, workbook cells and SVG text with Python's standard library alone. The `configuration_grid` test drives the window and covers file refusals and preview tokens.

A scenario's `setup` runs check scripts before the first step, and a step's `helpers` run them after it. A step with `fresh_process` first closes the application and starts another, whose evidence goes to `commands-N`.

The application-loop job also runs `release_geometry` against the release binary's kernel pin. It checks build, display, edit, undo/redo, save and reopen for crossing-cylinder loops, coaxial curved rims, concave pocket corners, fillets over earlier fillets at smaller and equal radii, through-hole mouths, blind-hole floors, through-bore shells and nonconvex shells. Each stage records the displayed body's volume, face and edge counts and persistent face names. The edit must move the volume the way its case expects. Undo must restore the built counts and names exactly and its volume within 1e-6 mm³, redo must match the edit, and reopen must match the saved part. A test runs the loop with an edit that changes nothing and requires that check to fail. All 24 STEP files must open directly as raw-valid solids under the pinned Catallax reader and OCP 8. Tangent-shadow equality and equal-cylinder crossing poles must return typed refusals and preserve the part. Evidence stays in the application-loop artifact's `release-geometry` directory. The existing `skew-corner-fillet` scenario and `fillet_corner_names` tests retain the V8 H geometry and persistent-reference checks.
