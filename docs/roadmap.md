# SolidDraft roadmap

This is a list of planned work in dependency order, not a release schedule. Progress is recorded by completed work, never by dates.

Status audited against main at `d57a2f163e39bb25ee2fdad400759adc88604eb7` on 8 November 2026, using source, checked-in scenarios and tests, git history and merged pull requests. **Shipped** below means merged application support within the stated limits; it does not mean a new release or a fresh runtime qualification. Section 10 lists only remaining work. The public [project website](https://kernel.zigrawbohnbawerick.org/) already exists; see section 8.

The companion document is [Catallax's roadmap](https://github.com/BohnBawerick/catallax/blob/main/docs/PLAN.md). SolidDraft and Catallax are one project in two repositories: SolidDraft is the application, Catallax is its kernel. This file orders the application work; Catallax's roadmap orders the kernel work. Where an item here needs a kernel item, it names the Catallax stage.

## 1. Premise

SolidDraft runs only on Catallax. Catallax is designed for the features SolidDraft's users drive, and SolidDraft grows step by step toward the most usable parts of SolidWorks and nTopology: parametric parts, drawings and assemblies on one side; implicit modelling, lattices, field-driven thickness, topology optimisation and simulation-led shapes on the other. The most usable features come first.

SolidDraft runs on Catallax. The former SMLib C++ kernel, its toolchain and its separate WebAssembly module have been removed. It is not kept as a fallback. A kernel kept in reserve is the half-commitment that Hanno Braun's Fornjot retrospective names as its project's biggest mistake, and keeping it would also keep the C++ toolchain, the second WebAssembly module and an interface shaped around a kernel we are not building.

## 2. What removing SMLib means for users

**Shipped:** [the Catallax backend](https://github.com/ZIGRAWBOHNBAWERICK/soliddraft/pull/3) and [SMLib removal](https://github.com/ZIGRAWBOHNBAWERICK/soliddraft/pull/6). The desktop, browser, command-line and server paths use Catallax. There is no C++ kernel, submodule or separate WebAssembly kernel module.

Unfinished commands remain visible and disabled with “Coming soon” ([waiting-feature interface](https://github.com/ZIGRAWBOHNBAWERICK/soliddraft/pull/140)). A saved part containing an unsupported feature rebuilds its available prefix and marks the feature with an error. That prefix is not a proved whole part and cannot export; it is not silently treated as a successful feature. [README.md](../README.md#what-works-today) and [the backend gaps](needs-catallax.md) describe the supported domains.

Sketches, extrudes, cuts, revolves, booleans, supported fillets/chamfers, drawings and exports already run on Catallax. Section 6 records their current limits rather than the former migration-day forecast.

## 3. The kernel boundary

The application keeps one boundary between itself and Catallax. Undo, rebuild and caching stay on the application side.

1. **Shipped:** a Catallax backend behind `soliddraft_kernel_api::Kernel`, selected in `soliddraft_app::kernel()` ([backend migration](https://github.com/ZIGRAWBOHNBAWERICK/soliddraft/pull/3)).
2. **Partial:** SMLib and its toolchain are removed ([removal](https://github.com/ZIGRAWBOHNBAWERICK/soliddraft/pull/6)); the interface still contains floating-point parameters, history, `FaceRole::Other`, `validate()` and `KernelError::InvalidResult`. Removing the old backend did not complete the interface cleanup.
3. **Partial:** origin sets, exact support queries and Catallax refusal codes cross the boundary ([origin references](https://github.com/ZIGRAWBOHNBAWERICK/soliddraft/pull/14), [exact axes and points](https://github.com/ZIGRAWBOHNBAWERICK/soliddraft/pull/209)). Exact rational input throughout the application interface remains work.
4. **Open:** rename the interface around Catallax and remove backend indirection after that cleanup. The trait still exists; its acceptance tests already run on Catallax.

The SMLib-specific dedicated kernel thread and process-isolation plan are retired. Desktop edit/proof workers are application responsiveness work, not the old global-state kernel thread. Browser construction and proof still run on the interface thread; section 10 keeps browser workers open.

**Shipped:** rebuild begins at the first changed feature and reuses immutable bodies under exact definition/input keys, with a byte-budgeted cache ([incremental rebuild](https://github.com/ZIGRAWBOHNBAWERICK/soliddraft/pull/13)). Renames build nothing; undo, redo and restoring a previous parameter value can reuse earlier bodies. Prepared builds and unchanged meshes are retained through the edit path ([edit-path reuse](https://github.com/ZIGRAWBOHNBAWERICK/soliddraft/pull/23), [offscreen mesh reuse](https://github.com/ZIGRAWBOHNBAWERICK/soliddraft/pull/135)). Cache accounting is an estimate of retained backend memory, not an exact kernel allocation census.

The development/scenario harness reports recomputed features, rebuilt meshes and placed bodies and compares against full replay. See [the rebuild cache](../crates/soliddraft-model/src/rebuild.rs), [the bracket scenario](../ci/scenarios/bracket.json) and [display-reuse scenario](../ci/scenarios/edit-display-reuse.json). Counters and comparison work stay outside normal model rebuilds.

## 4. One recipe format

**Open:** converge on `catallax-recipe`, following RECIPE.md section 6.2 in the Catallax repository. The current public recipe reader/writer still declares `soliddraft-recipe/1` in [format.rs](../crates/soliddraft-recipe/src/format.rs); native Catallax steps in evidence do not complete this migration. That section already maps `soliddraft-recipe/1`, including how `nearest` and `within` selectors become names resolved once against a built part. Old files and the existing corpus stay readable through a converter. The converter lives on the Catallax side, so both projects test it; switching the document model's file format is SolidDraft's work. The geometric digest stays as a test tool during the change and goes once agreement on point sets and names replaces it.

**Shipped:** persistent references resolve through Catallax origins ([origin-reference implementation](https://github.com/ZIGRAWBOHNBAWERICK/soliddraft/pull/14)); the survival regression is [references.json](../ci/scenarios/references.json). Catallax names faces by the operation that made them and reports origin sets through splits and merges, so the origin is the identity and the fingerprint is a check. The repair prompt for a genuinely lost reference stays. Geometric face-role guessing was removed from persistent-reference resolution. The interface cleanup in section 3 is separate from this completed naming change.

**Shipped scenario coverage:** reference survival is tested in the application loop. The scenario that edits the bracket's plate thickness and boss radius also renames features and reference planes, splits and merges faces with a later cut, suppresses and restores a feature, undoes and redoes, and saves and reopens the `.dwprt` file. After each step every reference resolves to the same origin or raises the repair prompt. The application never recovers a lost reference by picking the nearest face or by guessing an identity from geometry.

## 5. The application loop for agents

**Shipped:** [the headless application loop](https://github.com/ZIGRAWBOHNBAWERICK/soliddraft/pull/5), with later selectable-edit timing and drawing/rebuild coverage. [application-loop.md](application-loop.md) describes the current bundle and acceptance rules. Agents write most of the code, so this loop checks it end to end with no person at the keyboard. Catallax's roadmap calls it the application loop; the kernel loop is Catallax's `catallax-verify` command.

Headless SolidDraft on Catallax is driven by agents through `soliddraft mcp` and the command line, the same commands the assistant and the ribbon use. A scenario builds and edits parts the way a user does: sketches, features, parameter edits, undo, rollback, drawings. Each instrumented run saves a bundle:

- the recipe after every command;
- rendered views: hidden-line SVG from the existing `view` command, and raster screenshots made without a window by the same renderer the viewport uses;
- Catallax's per-operation log: how each decision was settled, refusals with their codes, marks, local tolerances and timings;
- elapsed time for each command, taken by the runner from outside the application and split into construction, edit, display (tessellation and rendering), measurement and refusal, next to Catallax's deterministic work counts;
- a pass or fail result for each check in the scenario.

A solid-producing command that returns before its visible selectable result has not completed the click interval. Explicit measurement is checked in its own interval. The scenario times the command through its visible selectable edit; SVG, measurement and exports have separate intervals. Wall-clock overruns are advisory in ordinary CI; strict release-path runs also reject over-budget results. Correctness, complete evidence and deterministic work limits remain hard checks. Timings sit beside the deterministic counts and do not replace them.

Measurement is test and development tooling. Timings, rebuild reports, survival checks, comparison runs and the scoreboard live in the scenario runner, the benchmarks, CI and the development build. None of it runs inside the application at runtime or slows a user edit, and measurement stays separate from the code path that builds the part. Checks that already run at runtime by design stay as they are; no new runtime work is added to them.

Kernel refusals retain portable questions for `catallax-verify`; failed application checks retain their recipe and available questions so the failure can be investigated and the scenario rerun. Because it is the same application users run, what the agents test is what users get. Scenario execution policy is maintained in [ci.md](ci.md).

## 7. Drawings on Catallax

**Shipped:** [Catallax drawings](https://github.com/ZIGRAWBOHNBAWERICK/soliddraft/pull/4), [drawing regeneration after edits](https://github.com/ZIGRAWBOHNBAWERICK/soliddraft/pull/40) and [curve accuracy labels](https://github.com/ZIGRAWBOHNBAWERICK/soliddraft/pull/46). [drawing.json](../ci/scenarios/drawing.json) builds, edits, regenerates and exports the part drawing as SVG, PDF and DXF. Exact silhouettes and remaining exact curve conversions are still open; assembly drawings are separate unfinished work.

Drawings use the polygon-mode pass (`mesh_hlr`) over Catallax's display triangles and edge polylines, with face origins preserved for associativity. Screen sections cut the preview mesh; exported sections subtract a half-space through Catallax booleans and hatch the cut-face loops. Whole lines and untrimmed circles retain their geometry after polygon visibility; other curves and silhouettes keep the polygon result. Exact silhouettes and the remaining curve conversions are Catallax requests. The drawing document, its associativity and its exporters keep their formats.

Every curve in a drawing says how accurate it is. Whole lines and untrimmed circles are exact. Silhouettes and other curves retain polygon geometry, and visibility is decided on polygons. Export uses certified meshes at their chord tolerance; the on-screen preview carries no such proof. The drawing document and its exports record which. A requested fit tolerance is never reported as a proven bound, and zero deviation measured at sampled points stays sampled. The labels tighten as exact silhouettes arrive from Catallax.
